================================================================================
EXECUTIVE SUMMARY
================================================================================

Bug: After executing INSERT via db->exec(), subsequent SELECT via 
     db->prepare()/db->step() returns no rows.

Root Cause: Transaction context mismatch in Berkeley DB storage manager

Result: SELECT returns DBSQL_DONE instead of DBSQL_ROW (empty result set)

================================================================================
THE PROBLEM IN ONE PICTURE
================================================================================

INSERT (via exec):
  OP_Transaction → sm->txn = 0x1f2f7f20 (active)
  OP_OpenWrite → cursor transaction = 0x1f31de10 (nested under sm->txn)
  INSERT data into nested transaction
  OP_Commit → commits sm->txn
  __sm_commit_txn → sm->txn = NULL  ← TRANSACTION CLEARED

SELECT (via prepare/step):
  [No OP_Transaction generated]
  sm->txn = NULL  ← NO ACTIVE TRANSACTION
  OP_OpenRead → creates new cursor transaction = 0x1f2f7f20 (new root-level)
  __sm_first → Berkeley DB returns DB_NOTFOUND
              (new transaction can't see data from different context)
  Result: EMPTY TABLE

================================================================================
PROOF FROM DEBUGGING
================================================================================

Transaction state during execution:

1. INSERT:
   __sm_cursor: sm->txn=0x1f2f7f20, creating cursor for db 3, write=1
     txn_begin result=0, smc->txn=0x1f31de10 (parent was 0x1f2f7f20)
                                                   ↑ NESTED

2. SELECT:
   __sm_cursor: sm->txn=(nil), creating cursor for db 3, write=0
     txn_begin result=0, smc->txn=0x1f2f7f20 (parent was (nil))
                                                   ↑ NEW ROOT-LEVEL

OP_Rewind output:
   __sm_first returned rc=0, res=1  ← res=1 means DB_NOTFOUND (empty)
   Final res=1, jumping=YES          ← SKIPS OVER RESULT SET

================================================================================
WHY THIS HAPPENS
================================================================================

1. SELECT Compilation Optimization:
   - SELECT is read-only, so compiler optimizes out OP_Transaction
   - Only write operations (INSERT/UPDATE/DELETE) get OP_Transaction
   - Result: sm->txn stays NULL when SELECT starts

2. Transaction Lifecycle:
   - INSERT's OP_Commit calls __sm_commit_txn()
   - __sm_commit_txn() explicitly sets sm->txn = 0
   - This is correct for cleanup, but leaves sm->txn = NULL for next statement

3. Berkeley DB MVCC:
   - Each transaction creates snapshot when it begins
   - Data in INSERT's nested transaction committed to sm->txn=0x1f2f7f20
   - SELECT creates NEW transaction at root level (NULL parent)
   - Different transaction contexts → data not visible to SELECT

RECOMMENDED SOLUTIONS
================================================================================

OPTION 1: Add OP_Transaction to SELECT (Preferred)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
File:      src/cg_select.c
Change:    Generate OP_Transaction opcode for SELECT statements
Effect:    Ensures sm->txn is active for READ operations
Benefit:   Consistent transaction handling across all statement types
Quality:   Best long-term solution

OPTION 2: Handle NULL sm->txn in __sm_cursor (Simpler)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
File:      src/sm.c (__sm_cursor function)
Change:    Use DB_READ_UNCOMMITTED flag when sm->txn is NULL
Effect:    Allows READ transactions to see committed data
Benefit:   Simpler, targeted fix; backward compatible
Quality:   Practical solution for immediate fix

OPTION 3: Begin read-only transaction automatically (Hybrid)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
File:      src/sm.c or vdbe.c
Change:    Auto-begin read-only transaction if sm->txn is NULL
Effect:    Similar to Option 1 but done at cursor level
Benefit:   Balance between Options 1 and 2

TEST CASE (Reproducible Bug)
================================================================================

#include <stdio.h>
#include "dbsql.h"

int main() {
    DBSQL *db;
    dbsql_stmt_t *stmt;
    char *errmsg = NULL;
    const char *tail;
    int rc, n_cols;
    const char **values, **cols;

    dbsql_create_env(&db, NULL, NULL, 0, 0);
    db->open(db, ":memory:", 0664, &errmsg);
    
    db->exec(db, "CREATE TABLE t (x INT)", NULL, NULL, &errmsg);
    db->exec(db, "INSERT INTO t VALUES (42)", NULL, NULL, &errmsg);
    
    db->prepare(db, "SELECT * FROM t", &tail, &stmt, &errmsg);
    rc = db->step(stmt, &n_cols, &values, &cols);
    
    // BUG: rc = -50978 (DBSQL_DONE, no rows)
    // EXPECTED: rc = -50979 (DBSQL_ROW, has data)
    printf("Bug: %d == DBSQL_DONE (want DBSQL_ROW)\n", rc);
    
    db->finalize(stmt, &errmsg);
    db->close(db);
    return 0;
}

================================================================================
CONCLUSION
================================================================================

This is not a memory corruption bug or random failure. It is a well-understood
architectural issue where:

1. INSERT operates in a transaction context (sm->txn active)
2. SELECT operates without transaction context (sm->txn = NULL)
3. Berkeley DB correctly prevents cross-context data visibility (MVCC)
4. Result: SELECT sees empty table

The root cause has been identified, the exact mechanism explained, debugging
evidence provided, and three solution approaches documented.

The fix requires either adding transaction support to SELECT or handling
NULL transaction context for READ operations - both are correct solutions
with different architectural implications.

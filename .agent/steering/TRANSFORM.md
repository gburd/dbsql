# Transform rules: SQLite 3.53.4 → dbsql

The SQLite-derived part of dbsql is **generated** by `dist/transpile`, a
deterministic transformer that runs over a pinned SQLite tag. Hand edits to
generated files go in the patch queue (`dist/transpile/patches/`) or into
hand-owned files, never into the output directly.

## Pipeline

```
fossil checkout version-3.53.4
  → select    (dist/transpile/manifest: upstream file → dbsql path)
  → generate  (upstream generators run on upstream sources: keywordhash.h,
               opcodes.h/.c, pragma.h, ctime.c, sqlite3.h for the API map)
  → rename    (token-level, scope-checked; rules + names.map + api.map)
  → restyle   (comment style, `name --` function headers, clang-format KNF)
  → patch     (dist/transpile/patches/NNNN-*.patch, applied in order)
  → src/      (committed)
```

There is no vendor branch. `src/` files derived from SQLite are always
regenerated by the tool. To move to a newer SQLite release, re-run the tool
with the new tag and refresh any patches that no longer apply.

The parsers (`sql_parser.y`, `fts5_parser.y`) are compiled by the vendored
lemon at build time. All other generated files are produced at transform time
and committed. `opcodes.h` carries compile-time asserts that every
`same as TK_x` opcode still equals its token value, so parser drift cannot
pass silently.

**Validation build.** `dist/transpile/run --native` also transforms SQLite's
own btree, pager and os layers into a scratch tree, and builds a testfixture
against them. SQLite's test suite must pass on that build. This shows the
transform preserves semantics, independently of the libdb storage manager.
The scratch tree is never committed or shipped.

`dist/transpile/run --tag version-3.53.4 --out src/` must produce a
byte-identical tree on every run. CI checks this.

## Naming

These rules follow the 2007 dbsql conventions and libdb's own.

| SQLite | dbsql | Rule |
|---|---|---|
| `sqlite3` (connection) | `DBSQL` | Public handle, uppercase like `DB_ENV` |
| `sqlite3_stmt` | `dbsql_stmt_t` | Public type (2007 dbsql spelling) |
| `sqlite3_value` | `dbsql_value_t` | Public type |
| `sqlite3_context` | `dbsql_func_t` | Public type (2007 dbsql spelling) |
| `sqlite3_str`, `_blob`, `_backup`, `_vtab`, `_module`, … | `dbsql_str_t`, `dbsql_blob_t`, … | Public types. Upper-case `DBSQL_BLOB` etc. are column-type constants, so handle types use lower-case `_t` |
| `sqlite3_foo(db, ...)` method-like API | `dbp->foo(dbp, ...)` | Method table on the handle |
| `sqlite3_foo(...)` free function | `dbsql_foo(...)` | Global API |
| `SQLITE_FOO` constants | `DBSQL_FOO` | Error codes are negative, in libdb style (§Errors) |
| `sqlite3FooBar()` internal | `__foo_bar()` | snake_case. If the result collides with a libdb or libc symbol or a system-header macro (for example `sqlite3Os*` vs libdb's `__os_*`), it becomes `__dbsql_foo_bar()` |
| `sqlite3Btree*`, `Btree`, `BtCursor` | `__sm_*`, `sm_t`, `sm_cursor_t` | the storage-manager seam (STORAGE.md) |
| `static fooBar()` | `__foo_bar()` (static) | Same rule |
| `Table`, `Expr`, `Select`, `Parse`, `Vdbe`, … | `table_t`, `expr_t`, `select_t`, `parser_t`, `vdbe_t`, … | `struct name` + `name_t` typedef |
| `Mem` | `mem_t` | |
| `VdbeCursor` | `vdbe_cursor_t` | |
| `u8 u16 u32 i64 u64` | `u_int8_t u_int16_t u_int32_t int64_t u_int64_t` | libdb types |
| struct fields: `zName nCol aCol pTab iDb` | `name n_col cols tab i_db` | **Readable names** (§Fields) |
| locals: `pParse pTab zSql regResult` | `parser tab sql reg_result` | **Readable names** (§Fields) |
| other camelCase functions (`exprCodeVector`) | `__expr_code_vector` | file-scope functions, static or not, are `__snake` |
| CamelCase macros (`ExprHasProperty`) | `EXPR_HAS_PROPERTY` | macros are upper case |
| `TK_*` `OP_*` `EP_*` `TF_*` `SF_*` `WHERE_*` `MEM_*` | unchanged | Internal enum/flag macros stay as-is: they are the language of the VDBE and parser, and keeping them makes upstream diffs readable |

### Fields and locals

The upstream Hungarian prefixes are rewritten to plain readable names:

- `p`, `z`, `x`, `b`, `e`, `pp`, `pz` (pointer, string, callback, boolean,
  enum code) are dropped: `pTab → tab`, `zName → name`, `xFunc → func`,
  `eType → type`. Override: `pParse → parser`.
- `a`, `ai`, `ap`, `az`, `aa` (arrays) become the plural: `aCol → cols`,
  `aOp → ops`, `azArg → args`.
- `n` (count) and `i` (index) are kept as a separate word: `nCol → n_col`,
  `nKeyField → n_key_field`, `iDb → i_db`.
- Everything else in camelCase becomes snake_case: `regResult → reg_result`,
  `tabFlags → tab_flags`.

Renaming is done by token text. The same name maps the same way in every
file, for locals and struct fields alike. The tool checks every scope (each
function body, struct body and macro definition) and requires the rename to
be one-to-one there. On a collision, a name falls back to its prefixed form
(`p_tab`, `a_col`). If that also collides, the build fails until an override
is added to `dist/transpile/names.map`. Overrides can be global (`pTab tab`)
or limited to one function's locals (`func:pTab ptab`). Results that would
be C or C++ keywords use the fallback form too.

The upstream comment text is kept, with identifiers inside comments renamed
using the same map.

## Result codes

`DBSQL_*` result codes keep SQLite's numeric values (`DBSQL_OK` 0,
`DBSQL_ERROR` 1, …, `DBSQL_ROW` 100, `DBSQL_DONE` 101), and extended codes
are `primary | (n << 8)`. The engine relies on that arithmetic (`rc & 0xff`)
in hundreds of places, so changing the values would be a rewrite, not a
rename. These codes are their own namespace, separate from errno and from
libdb's negative codes. `dbsql_strerror()` describes every code. The storage
manager converts libdb errors to DBSQL codes at the sm/ boundary.

## SQL-visible names

SQL-level reserved names use the `dbsql_` prefix: `dbsql_schema` (with
`dbsql_master` as an alias), `dbsql_temp_schema`, `dbsql_sequence`,
`dbsql_stat1`/`dbsql_stat4`, `dbsql_version()`, `dbsql_source_id()`,
`dbsql_compileoption_used()`, and `dbsql_autoindex_*`. The transform
rewrites them inside string literals. The test runner applies the same
substitution to SQLite's `.test` scripts.

## Prototypes and headers

Internal prototypes stay where upstream keeps them (`dbsql_int.h`, from
sqliteInt.h). Hand-written files (src/sm, src/os, src/api glue) use libdb's
`PUBLIC:` comment lines, and `dist/s_include` generates `src/inc/*_ext.h`
from them.
